Python Bindings and Packaging
============================

# Python Interface

The wrapper interface uses an object-based interface instead of explicitly passing device and object on every call.

`anariFooBar(device, object, ...)` turns into `object.fooBar(...)`.

Object lifetime is automatically handled and doesn't require explicit calls to retain/release. 

See `examples/python/anari_tutorial_device.py` for an example.

# Frontend Python Bindings

The SDK python bindings consist of two layers. The raw cffi bindings generated by `code_gen/cffi_gen.py` and a python wrapper generated from `code_gen/__init__.py.in`. They are built via the `neo_bindings` CMake target.

## Installing

Binary wheels are built for Linux (manylinux_2_28 and musllinux_1_2, x86_64
and aarch64), macOS (arm64 and x86_64, macOS 11+) and Windows (AMD64), with
cibuildwheel (see Building). Install one with pip:

```
pip install wheelhouse/anari-*.whl
```

```python
import anari

library = anari.loadLibrary('sink')   # sample devices ship in the wheel
device = library.newDevice('default')
```

`anari.loadLibrary(name)` loads the libraries shipped in the package
(`anari.library_dir()`: the `sink` and `debug` sample devices) from the
package, and any other name through the frontend's usual search.
`'name,<directory>/'` loads a device from a given directory. Devices and
objects keep their library loaded, so they can be released in any order.

## Building

The package is built from the `pyproject.toml` in the SDK's root directory with
[py-build-cmake](https://github.com/tttapa/py-build-cmake). Either directly from github:
```pip3 install git+https://github.com/KhronosGroup/ANARI-SDK```

or from an already checked out version of the repo via either
```pip3 install ANARI_SDK/```
or
```python3 -m build ANARI-SDK/```

The build configures the SDK with only the frontend, helium, the `sink` and
`debug` devices and the bindings (`ANARI_PYTHON_WHEEL=ON`; see
`[tool.py-build-cmake.cmake.options]`). On macOS, set
`MACOSX_DEPLOYMENT_TARGET` and `ARCHFLAGS` in the environment: py-build-cmake
passes them on as `CMAKE_OSX_DEPLOYMENT_TARGET` and `CMAKE_OSX_ARCHITECTURES`
(cross-compiling when `ARCHFLAGS` names another architecture than the
interpreter's) and uses them for the wheel's platform tag. cibuildwheel builds
dual-architecture wheels, one per architecture (`-arch arm64` and
`-arch x86_64`), with a deployment target of 11.0 (`[tool.cibuildwheel.macos]`).

Portable wheels (manylinux, musllinux, macOS and Windows, for every supported
CPython) are built with [cibuildwheel](https://cibuildwheel.pypa.io), configured
in `[tool.cibuildwheel]`:
```cibuildwheel --output-dir wheelhouse```

## Wheel contents

```
anari/
  __init__.py, utils.py, __main__.py   Python wrapper (generated) and CLI
  anari_api.{so,pyd}                   cffi bindings, frontend linked statically
  msvcp140*.dll, vcruntime140*.dll     Windows only: the MSVC runtime
  sdk/                                 the ANARI SDK, installed as a prefix
    include/                           anari/anari.h, anari_cpp, backend/helium
    lib/ (and bin/ on Windows)         libanari, helium, anari_backend, ...,
                                       anari_library_sink, anari_library_debug
    lib/cmake/anari-<version>/         anariConfig.cmake
    share/anari/code_gen/              anari_generate_queries() scripts + JSON
```

The wheels have no dependencies outside themselves but the operating system's
base libraries (glibc or musl, libstdc++, macOS' libc++ and libSystem, Windows'
system DLLs); the validation suite (`tests/python`) checks this. On Windows
everything uses the dynamic MSVC runtime (`/MD`, CMake's default) so that the
static `helium` and `anari_backend` libraries in the wheel link with vendors'
default builds; the wheel carries that runtime next to `anari_api.pyd`.

## Building a device against the wheel

The wheel is an ANARI SDK: a device can be built with nothing but
`pip install anari`, a compiler and CMake.

```
python -m anari --cmake-dir     # anari_DIR, for find_package(anari)
python -m anari --include-dir
python -m anari --library-dir
python -m anari --version
```

```
cmake -S my_device -B build -Danari_DIR="$(python -m anari --cmake-dir)"
```

`find_package(anari)` then provides `anari::helium`, `anari::anari` and
`anari_generate_queries()` (code_gen runs with the Python that configures the
build). `examples/empty_helium_device` builds this way; the validation suite
builds it and renders with it.


# Device Bindings

Devices are exposed through their own python package containing the device library (eg. `libanari_library_helide.so`) and a `__init__.py` that is generated from `code_gen/device_trampoline.py.in`. The trampoline file simply imports the `anari` frontend module and loads the device specific library.

This mechanism is chosen to allow all modules to be self contained. Python packages don't have an intrinsic mechanism to determine each others install locations making their contents not easily accessible to the frontend module `loadLibrary` function. Instead by importing for example `import helide` the helide module provides its own location and can inject the library location into a `newDevice` wrapper without making assumptions about install locations.

The plain `anari` module can still be used the same way as the C API. Using `anari.loadLibrary('helide')` will find a system installed helide device but not one installed as a python package.

## Readying a Device for Packaging

### CMake additions

To setup a device for packaging its `CMakeLists.txt` needs to configure the trampoline file:
```
set(DEVICE_LIBRARY_NAME helide)
configure_file(${ANARI_CODE_GEN_ROOT}/device_trampoline.py.in ${CMAKE_CURRENT_BINARY_DIR}/__init__.py)
```

and add install targets for the configured file and the library in a component specific to the python bindings (`COMPONENT helide_module` here). These install targets will determine what gets put into the package.
```
install(
  FILES ${CMAKE_CURRENT_BINARY_DIR}/__init__.py
  EXCLUDE_FROM_ALL
  COMPONENT helide_module
  DESTINATION helide/)
install(TARGETS anari_library_helide
  EXCLUDE_FROM_ALL
  COMPONENT helide_module
  LIBRARY DESTINATION helide
  RUNTIME DESTINATION helide)
```

### pyproject.toml

Write a `pyproject.toml` file using the py-build-cmake build backend by configuring the build in the
`[tool.py-build-cmake.*]` sections.

`install_components` should match the component name from the previous step.

```
[project] # Project metadata
name = "helide"
requires-python = ">=3.7"
readme = "README.md"
license = "APACHE"
license-files = ["LICENSE"]
dependencies = ["cffi","anari"]
version = "1.0"

[build-system] # How pip and other frontends should build this project
requires = ["py-build-cmake~=0.5.0"]
build-backend = "py_build_cmake.build"

[tool.py-build-cmake.sdist]
include = ['*']

[tool.py-build-cmake.module]
generated = "package"

[tool.py-build-cmake.cmake] # How to build the CMake project
build_type = "RelWithDebInfo"
source_path = "."
build_args = ["-j"]
install_components = ["helide_module"]
```

### Building against the `anari` package

A device package can build against the ANARI SDK in the `anari` package instead
of a separately installed SDK: make `anari` a
build requirement as well as a dependency, of the SDK release series the
device's ABI (`anari/backend`) comes from, and point CMake at the package's SDK
in the device's `CMakeLists.txt` when py-build-cmake runs it:

```
[project]
dependencies = ["anari~=0.17.0"]

[build-system]
requires = ["py-build-cmake~=0.5.1", "anari~=0.17.0"]
```

```
if (DEFINED PY_BUILD_CMAKE_VERSION AND NOT anari_DIR)
  execute_process(
    COMMAND ${PY_BUILD_CMAKE_BUILD_PYTHON_INTERPRETER} -m anari --cmake-dir
    OUTPUT_VARIABLE anari_DIR OUTPUT_STRIP_TRAILING_WHITESPACE)
endif()
find_package(anari REQUIRED)
```

`examples/empty_helium_device` (`hecore`) is set up this way: `pip install
examples/empty_helium_device` builds it against the installed `anari` and
installs the `hecore` package (`import hecore; device = hecore.newDevice()`).
The validation suite does this with nothing downloaded.

## Building "portable" Packages

[cibuildwheel](https://github.com/pypa/cibuildwheel) is a tool to create portable packages for upload to package repositories. It builds the package in a variety of standardized environments (containers) that allow the packages to be binary compatible with various target systems.

For simple packages like the anari frontend this works without much effort since it has no dependencies other than "usual" system libraries (standard library, libdl etc.).

Device libraries however are likely to have non-trivial dependencies like graphics APIs, CUDA etc.. For the build in the container to work these dependencies likely need to be installed since the containers are minimal. This can be done via the `before-all` step (or fetch content in the cmake build etc.).

However since those dependencies are not part of the standardized base environment cibuildwheel will detect what other `.so` the packaged device library depends on and include them in the package. This bloats the package and more importantly probably leads to the package "shipping" third party binaries/code.

If the device for example relies on OpenGL one could apt install the required packages (mesa etc.) in the `before-all` step and just naively add `OpenGL::OpenGL` to the `target_link_libraries`. This would then likely lead to libgl.so and other parts of the mesa infrastructure to get copied into the package which is likely undesirable.

To avoid this issue the device should be kept clean of dynamic link dependencies. In the above opengl example this could be accomplished by using a gl loader library like [glad](https://github.com/dav1dde/glad) which will fetch the entrypoints dynamically (`dlsym` etc.) instead of linking against it at compile time triggering the package inclusion.
